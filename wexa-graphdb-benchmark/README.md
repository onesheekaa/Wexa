# CognoDB Cloud vs. Four Managed/Self-Hosted Graph Databases

A reproducible benchmark comparing [CognoDB Cloud](https://console.cognodb.com) against
Neo4j, Memgraph, ArangoDB, and Dgraph on identical hardware, an identical dataset, and
identical query workloads.

## 1. Platforms compared

| Platform | Deployment | Query language | Why it's here |
|---|---|---|---|
| CognoDB Cloud | Managed cloud, free `c0` tier | Cypher over Bolt | The subject of the assignment |
| Neo4j Community 5 | Self-hosted (Docker) | Cypher over Bolt | Closest apples-to-apples comparison — CognoDB speaks the same protocol |
| Memgraph | Self-hosted (Docker) | Cypher over Bolt | In-memory graph engine — tests whether storage model beats query language as the deciding factor |
| ArangoDB 3.11 | Self-hosted (Docker) | AQL | Multi-model (document + graph) — a genuinely different engine, not just another Cypher dialect |
| Dgraph | Self-hosted (Docker) | DQL | Distributed triple-store design — different data model entirely |

**Why self-hosted instead of four more cloud trials:** the assignment explicitly allows
"free tiers, free trials or self-hosted deployments capped to the same resources"
(section 4). Four extra cloud signups (several requiring cards even on a "free" trial)
would burn a meaningful chunk of the 48-hour window for no benefit to the comparison —
Docker resource limits give exact, auditable parity instead of trusting four different
vendors' definitions of "free tier." This is a deliberate methodology choice, not a
shortcut; see the fairness section below.

## 2. Fairness — same resources everywhere

CognoDB's free tier is fixed at **burstable 0.5 vCPU, 256 MB RAM, 1 GB disk**. Every
self-hosted container in `docker-compose.yml` is capped to match:

| Platform | vCPU | RAM | Disk |
|---|---|---|---|
| CognoDB Cloud | 0.5 (burstable) | 256 MB | 1 GB |
| Neo4j | 0.5 (`cpus: 0.5`) | 256 MB (`mem_limit: 256m`) | _(see caveat below)_ |
| Memgraph | 0.5 | 256 MB | _(see caveat below)_ |
| ArangoDB | 0.5 | 256 MB | _(see caveat below)_ |
| Dgraph (zero+alpha combined) | 0.5 | 256 MB | _(see caveat below)_ |

**Caveat, stated honestly:** Docker's `mem_limit`/`cpus` enforce CPU and memory hard
limits, but there's no equivalent one-line disk quota without a specific storage
driver/filesystem setup. Disk usage is instead measured after each load with
`docker exec <container> du -sh <data-dir>` and recorded by hand in the footprint table
below, rather than silently left unmeasured.

## 3. Dataset

**ca-AstroPh** (SNAP) — an arXiv Astrophysics co-authorship network.
Source: https://snap.stanford.edu/data/ca-AstroPh.html
Cite as: J. Leskovec, A. Krevl. *SNAP Datasets: Stanford Large Network Dataset
Collection.* http://snap.stanford.edu/data (2014).

- Nodes: 18,772
- Relationships: 198,110 (within the assignment's 100k–500k target range)
- The dataset has no natural "label" field; each node is assigned one of four synthetic
  labels (`core` / `collaborator` / `prolific` / `occasional`) with a fixed random seed,
  purely so the filtered-lookup and aggregation workloads have something to filter or
  group on. This overlay is disclosed here, not hidden — it has no bearing on which
  platform "wins," since it's applied identically everywhere.

Built by `python -m src.dataset`, which downloads the raw edge list and writes
`data/nodes.csv` / `data/edges.csv`.

## 6. Methodology notes

- **Warm-up:** 20 iterations discarded before every timed read workload, per the
  assignment's suggestion.
- **Iterations:** 100 per read workload, percentiles (p50/p95) reported, not just means.
- **Mixed workload:** concurrency swept at 1 / 10 / 40 clients, 20% write / 80% read mix,
  30 seconds sustained per concurrency level, each client on its own connection.
- **Same client, same region:** all runs executed from `<fill in: your machine / cloud
  region>` against every platform in the same session, to avoid attributing network
  variance to the database itself.
- **Indexes:** documented per-platform in each adapter's `create_indexes()` return value
  and reproduced in `results/*.json` under `ingest.index_report`.

## 8. Reproducing this benchmark

**Prerequisites:** Docker, Python 3.10+, a free CognoDB account.

```bash
git clone <this-repo-url>
cd wexa-graphdb-benchmark
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

cp .env.example .env
# edit .env: fill in your CognoDB URI + password from the console
# (self-hosted platform credentials in .env.example already match docker-compose.yml)

./scripts/run_all.sh
```

This brings up Neo4j/Memgraph/ArangoDB/Dgraph via Docker, builds the dataset, runs the
full workload suite against all five platforms, and regenerates `RESULTS.md`.

To run a single platform: `python -m src.runner --platform neo4j`
